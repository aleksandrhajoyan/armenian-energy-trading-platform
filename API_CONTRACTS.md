# API Contracts

HTTP API design principles for the FastAPI surface. Only endpoints listed as **implemented** are live.

## Status

| Item | State |
| --- | --- |
| Runtime API | Minimal FastAPI app factory (`create_app`) |
| Routers | Health router under `/api/v1` |
| OpenAPI schema | Generated by FastAPI at runtime; not a published contract file |
| Endpoints | `GET /api/v1/health` implemented; remaining business endpoints **TBD** |

## Design principles

- The API is a **transport adapter**. Business logic lives in application use cases, not in routers.
- Request and response bodies use **canonical contracts** (or thin HTTP wrappers around them). Vendor CSV/Excel/PDF shapes must not appear on the public API.
- Routers call use cases / the Chief Orchestrator Agent port. They do not import infrastructure adapters or ML trainers.
- The API / composition root wires implementations into application ports. It does not contain market formulas.
- Idempotency for workflow-triggering commands will be defined when those endpoints exist.
- Authentication/authorization model is **TBD** (not specified in this chunk).

## Versioning

- Public HTTP routes are prefixed with `/api/v1`.
- Breaking changes require a new version prefix. Additive optional fields on canonical contracts should remain backward compatible.
- Internal Python module layout is independent of the URL version.

## Canonical request / response

- Successful JSON responses wrap or directly serialize canonical Pydantic models defined in the domain (implementation in later chunks), or thin HTTP-specific models such as health.
- Collection responses should include stable pagination fields when lists are introduced (schema TBD).
- Clients never send raw Armenian-header tables to domain endpoints; upload/ingest endpoints, if added, terminate in infrastructure adapters.

## Standard error envelope (concept)

All error responses should share a single envelope, for example:

- `error_code` — stable machine code
- `message` — safe human message (no secrets)
- `details` — optional structured field errors
- `correlation_id` — request/workflow correlation
- `workflow_id` — present when the error belongs to an orchestration run

HTTP status codes remain standard (`400` validation, `404` missing, `409` conflict, `422` unprocessable canonical payload, `500` unexpected). Mapping from domain errors to status codes is an API-layer duty. The health endpoint does not yet use this envelope.

## Correlation / workflow ID

- Every request should accept or mint a **correlation ID** (header concept: `X-Correlation-ID`, name configurable).
- Orchestrated DAM runs also carry a **workflow ID** distinct from HTTP correlation when a run is persisted.
- Both IDs propagate into logs, `AdapterDiagnostic`, and `DLQRecord`.
- Not implemented on the health endpoint.

## Endpoints

### `GET /api/v1/health` (implemented)

Process/application liveness for this FastAPI process only.

| | |
| --- | --- |
| **Purpose** | Confirm that the HTTP application is serving. Used by local development and later process probes. |
| **Auth** | None |
| **Request body** | None |
| **Side effects** | None. Does not open database, Redis, Qdrant, ML, LLM, or external connections. |

**HTTP 200** JSON body:

| Field | Type | Meaning |
| --- | --- | --- |
| `status` | `"ok"` | This process is serving HTTP. |
| `service` | string | Configured application name (`APP_NAME`). |
| `environment` | `"development"` \| `"test"` \| `"production"` | Configured application environment (`APP_ENV`). |

This is **not** an infrastructure readiness check. A 200 response does **not** mean PostgreSQL, TimescaleDB, Redis, Qdrant, LangGraph, ML models, or any external service is healthy. Those systems are not implemented.

Candidate families still unspecified until later chunks (Phase 9 and any explicitly scoped earlier slice):

- Readiness (when infrastructure exists)
- Workflow start / status (Chief Orchestrator Agent)
- Canonical reads (forecasts, bids, settlements)
- Ingest triggers (files) — must land on adapters, not agents
